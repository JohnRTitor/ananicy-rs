# Fedora packaging recipe

`ananicy-rs.spec` is a **community-maintained recipe**. It is not carried by
Fedora, has not been through Fedora review, and its presence here does not mean
Fedora supports the package. Submitting it to Fedora would be a separate
exercise with a separate review.

- recipe: [`ananicy-rs.spec`](ananicy-rs.spec)
- vendored dependencies: generated by [`make-vendor-archive.sh`](make-vendor-archive.sh)

## Build it

```bash
# 1. The upstream sources: the git archive of the release tag, as the release
#    workflow attaches it. `%autosetup -n ananicy-rs-<version>` also accepts
#    GitHub's own /archive/v<version>.tar.gz if you prefer that as Source0.
version=$(sed -n '/^\[workspace\.package\]/,/^\[/s/^version = "\([^"]*\)"/\1/p' Cargo.toml | head -n1)
mkdir -p ~/rpmbuild/SOURCES
git archive --format=tar --prefix="ananicy-rs-$version/" HEAD \
  | gzip -n -9 > ~/rpmbuild/SOURCES/ananicy-rs-$version.tar.gz

# 2. The Cargo dependencies, vendored. Needs cargo, tar and xz.
./contrib/fedora/make-vendor-archive.sh

# 3. Build.
rpmbuild -bs contrib/fedora/ananicy-rs.spec   # source rpm
rpmbuild -ba contrib/fedora/ananicy-rs.spec   # binary rpm
```

The usual Fedora loop is `rpmbuild -bs` followed by
`mock -r fedora-$release --rebuild ananicy-rs-0.1.0-1.src.rpm`, which is also
how `.github/workflows/packaging.yml` builds it in CI.

Regenerate the vendor archive whenever `Cargo.lock` changes, and re-upload it
with the source package. Set `SOURCE_DATE_EPOCH` to the release date to get
byte-identical archives for an unchanged lockfile.

## Static validation

```bash
rpmspec --parse contrib/fedora/ananicy-rs.spec     # syntax and tag structure
rpmbuild -bs contrib/fedora/ananicy-rs.spec        # source package
rpmlint contrib/fedora/ananicy-rs.spec             # if rpmlint is installed
```

What these reported while the recipe was written, with `rpmlint` 2.10.0:

| Report | Verdict |
| --- | --- |
| `invalid-url Source1` | expected. The vendor archive is generated on the packager's machine by `make-vendor-archive.sh` and uploaded with the source package; there is no URL for rpmlint to check. |
| `no-buildroot-tag` | obsolete. `BuildRoot` has not been required since rpm 4.6. |
| `no-packager-tag`, `no-group-tag` | artefacts of a `rpmlint` run outside Fedora. Fedora's build system sets `Packager`, and `Group:` no longer exists in modern rpm. |
| `invalid-license GPL-3.0-only` | an artefact of a PyPI `rpmlint` install, whose `ValidLicenses` list is empty. `GPL-3.0-only` is the SPDX identifier Fedora wants, and the one `Cargo.toml` itself uses. |
| `no-signature` | an unsigned local build. |

`make-vendor-archive.sh` was run and produced a 14.5 MB
`ananicy-rs-0.1.0-vendor.tar.xz` holding 197 crates plus the source-replacement
config, and `rpmbuild -bs` consumed it. The `%prep` version check was exercised
in both directions.

**What the CI job found, and what is now verified.** `rpmbuild -ba` had not been
run when this recipe was written — there is no Fedora build environment in the
environment it was written in — so the sections above record what was checked
without one. It is now built on every change in a `fedora:latest` container, and
the package contains exactly the table above plus a build-id link, and rpm's
automatic `ananicy-rs-debuginfo` subpackage, which also ships the sources under
`/usr/src/debug/` as usual for a Rust package. `rpmlint` reports the two warnings
in the table and nothing else. A real submission still wants
`mock -r fedora-rawhide --rebuild`, which builds in a proper buildroot as an
unprivileged user rather than as root in the job's own filesystem.

## `%check`, and why the CI job runs it separately

`%check` is `cargo test --locked --offline` in the dev profile, and it is correct
as written: under mock and Koji it runs as the build user, which is not root, and
the cgroup tests in `ananicy-platform` skip themselves with a message when the
suite is unprivileged.

The CI job does not use mock, and a bare `rpmbuild -ba` runs the build as root,
where those tests are not merely privileged but unreliable. Three of them share
the name `UNIT_TEST_ANANICY` and each removes it on the way out, so as root they
race each other — the project's own `ci.yml` has been failing this way on
`ubuntu-latest`, at `cgroups.rs:132` with "the cgroup directory must exist" — and
on a runner whose `/sys/fs/cgroup` is read-only the two that assert a successful
`create_cgroup` fail outright. None of that says anything about this package.

So the job runs `rpmbuild -ba --nocheck` and then runs the same suite, against the
same source, vendor tree and `CARGO_HOME` that `%check` would have used, as an
unprivileged user. Same coverage, same commands, no test skipped, and it matches
what the Debian and Arch jobs do — `Rules-Requires-Root: no` and `makepkg` are
both unprivileged by construction.

## What goes in the package

| Path | From |
| --- | --- |
| `/usr/bin/ananicy-rs` | `make install` |
| `/usr/lib/systemd/system/ananicy-rs.service` | `make install`, from `data/ananicy-rs.service.in` |
| `/etc/ananicy.d/` | packaged empty; the daemon writes `ananicy.conf` into it on first start |
| `/usr/share/bash-completion/completions/ananicy-rs` | `ananicy-rs completions bash` |
| `/usr/share/fish/vendor_completions.d/ananicy-rs.fish` | `ananicy-rs completions fish` |
| `/usr/share/zsh/site-functions/_ananicy-rs` | `ananicy-rs completions zsh` |
| `/usr/share/doc/ananicy-rs/` | `README.md`, `CONTRIBUTING.md`, `docs/*.md` |
| `/usr/share/licenses/ananicy-rs/LICENSE` | `LICENSE` |

There are no man pages to install: the project has none. `docs/CLI.md` and
`docs/CONFIGURATION.md` are the reference material instead.

`make install` is called rather than a hand-rolled install, so the binary, its
mode and the unit are byte-for-byte the same as every other recipe under
`contrib/`. The unit's `@bindir@` placeholder resolves to `/usr/bin`.

## Dependencies

`BuildRequires` covers exactly what the default feature set needs:

| Package | Why |
| --- | --- |
| `cargo`, `rust >= 1.85` | the build itself; 1.85 is the first release that understands edition 2024 |
| `make` | `make install` |
| `pkgconf-pkg-config`, `pcre2-devel` | `pcre2-sys` links `libpcre2-8`; see below |
| `systemd-devel` | the default `systemd` feature declares `#[link(name = "systemd")]` |
| `systemd-rpm-macros` | `%systemd_post`, `%systemd_preun`, `%systemd_postun_with_restart` |

There is no manual `Requires:`. rpm derives `pcre2` and `systemd-libs` from the
SONAMEs the linker records, and nothing more is needed: `ananicy-rs start` also
runs without systemd, so requiring systemd-as-init would be wrong.

`gcc` is not listed because `pcre2-devel` and `systemd-devel` both require it.

### Why `pcre2-devel` is required and not optional

`pcre2-sys` first asks `pkg-config` for `libpcre2-8` and only builds its own
vendored copy when the probe fails. Both paths compile, but they are not the
same build: the vendored copy is compiled with `SUPPORT_JIT=1` forced and linked
statically. Without `pcre2-devel` the package would silently ship a differently
configured regex engine from the one every other build of this daemon uses.

## Why Cargo dependencies are vendored

None of the four workspace crates — `ananicy-rs`, `ananicy-core`,
`ananicy-platform`, `ananicy-bpf` — is published on crates.io, so Fedora's
`%cargo_prep`, which derives the build requirements from a crate's crates.io
metadata, cannot be used. The next option, listing every transitive crate as a
`BuildRequires: rust-<crate>-devel`, is what that macro generates and would mean
around two hundred dependencies for one binary.

So the recipe carries a `Source1` with every crate in `Cargo.lock` vendored, and
builds with `--offline`. That is not a workaround for a missing feature; it is
required anyway, because Fedora builds have no network access and `%build`
cannot fetch anything.

`CARGO_HOME` is pointed inside the build directory, and `CARGO_NET_OFFLINE` is
implied by `--offline`, so a build reads nothing from the build user's home
directory and cannot silently reach out.

The vendored tree is roughly 135 MB unpacked and 15 MB compressed. It is
generated on demand and gitignored; it is not committed to this repository.

## Features

The recipe builds the default feature set, which is `netlink` plus `systemd`:
the netlink connector for process events, and `sd_notify`/journald integration.

The `bpf` feature is deliberately not enabled:

- it is not the default, and the canonical build in `README.md` and
  `docs/BUILD.md` is `cargo build --release`;
- it needs `clang`, `libbpf` and `rustfmt` at build time, so a build that turned
  it on would need the whole eBPF toolchain;
- it needs `CAP_BPF` and `CAP_PERFMON` at run time, and the unit shipped in
  `data/ananicy-rs.service.in` does not grant them. Enabling the feature would
  produce a binary whose event source cannot start under the unit this package
  installs.

`ananicy-rs` has no fallback from netlink to eBPF, but it does have a fallback
the other way: if the BPF monitor fails to start it warns and uses netlink. So a
future `-bpf` subpackage would be a runtime opt-in, not a replacement.

## systemd

The unit is the one upstream ships, unchanged — `data/ananicy-rs.service.in`
with `@bindir@` substituted. Its hardening, `Nice=-5`, `OOMScoreAdjust=-999`,
`Delegate=yes` and `CapabilityBoundingSet` are all upstream's decisions and none
of them is relaxed here. The packaging adds only registration:

- `%systemd_post` runs `systemctl preset` and rpm's file triggers reload systemd
  when the unit appears, changes or disappears.
- `%systemd_preun` stops the service before the binary is removed.
- `%systemd_postun_with_restart` restarts the service on upgrade, but only if it
  was running.

The service is **not started on install and not enabled on install**.
Installing a package should not begin reprioritising the machine's processes;
enabling is the administrator's decision:

```bash
sudo systemctl enable --now ananicy-rs.service
```

## Rules

`ananicy-rs` ships no rules. It reads `*.rules`, `*.types` and `*.cgroups` from
`/etc/ananicy.d` (recursively, sorted by path) and writes a default
`ananicy.conf` there on its first start. Copy a rule set in before enabling the
service, from <https://gitlab.com/ananicy-cpp/ananicy-cpp> or
<https://github.com/Nefelim4ag/Ananicy>.

`/etc/ananicy.d` is packaged as an empty directory and nothing inside it is a
`%config` file. Shipping a default `ananicy.conf` would shadow the one the
daemon writes for itself, and would turn a file the administrator is expected to
own into one rpm has to reconcile on every upgrade.

Neither Fedora nor any other distribution currently carries `ananicy-cpp`, so
the recipe declares no dependency on a rule set. If one is packaged later, the
right relationship is a `Recommends` on the daemon, or a separate
`ananicy-rs-rules` subpackage, not a `Requires`.

## Known limitations

- `Version:` is a literal in the spec. `%prep` compares it against
  `Cargo.toml` and fails the build on a mismatch rather than shipping a
  mislabelled package, but a real Fedora submission would use
  `Changelog: *:date git Author` with `%autochangelog`, which needs a signed-off
  `v<version>` git tag.
- The recipe has not been submitted to, or reviewed by, Fedora. It is a starting
  point for a submission, not a finished one.
- No `Conflicts: ananicy-cpp`. Two auto-nicing daemons on one machine is a
  genuine conflict, but `ananicy-cpp` is not in Fedora, and a `Conflicts:` on a
  package that does not exist is a guess.
